# 체계적 디버깅 (debugging)

추측으로 고치지 않는다. **재현 → 범위 좁히기 → 가설 하나씩 검증 → 근본 원인 수정 → 회귀 시험** 순서로 간다.

## 1. 재현
- 오류 메시지·스택을 **원문 그대로** 확보한다(사용자가 준 것 또는 직접 실행). 줄 번호·예외 종류·마지막 사용자 코드 프레임을 적는다.
- 가장 짧은 재현 명령을 만든다. 재현이 안 되면 환경 차이(버전·OS·경로·인코딩·환경 변수·작업 폴더)를 먼저 의심하고 비교한다.
- 윈도우 특이점: 경로 역슬래시, CRLF, 콘솔 코드 페이지(cp949/65001)·BOM, PowerShell 과 bash 문법 차이, 파일 잠금.

## 2. 범위 좁히기
- 스택의 맨 아래(가장 깊은 사용자 코드)부터 Read 한다.
- 입력을 반으로 줄여 가며(이분 탐색) 실패하는 최소 입력을 찾는다. 최근 바뀐 코드가 의심되면 `git log -p -- <파일>` · `git bisect` 를 쓴다.
- 값 확인은 작은 출력(로그 한 줄)이나 짧은 스크립트로. 확인이 끝나면 넣은 출력은 지운다.

## 3. 가설 → 검증 (한 번에 하나)
TodoWrite 에 가설을 적고 하나씩 지운다:
```
가설: 첫 줄에 BOM(﻿)이 붙어 float() 가 실패한다
검증: repr(sys.stdin.readline()) 출력 → '﻿10 + 20\n'  ✔ 확인
```
- 검증 결과가 가설과 다르면 그 가설을 버리고 다음으로. 같은 수정을 반복 시도하지 않는다(두 번 실패하면 접근을 바꾼다).
- 막히면 AskAI 로 다른 AI 에게 **재현 명령·오류 원문·관련 코드 조각**만 보내 의견을 받는다(비밀·개인정보 제외).

## 4. 근본 원인 수정
- 증상을 덮는 우회(예외 삼키기, 특수 문자 지우기, 재시도 늘리기)보다 원인을 고친다. 우회가 불가피하면 왜인지 주석과 보고에 남긴다.
- **도구·환경이 원인이면 사용자 코드에 땜질하지 말고** 사용자에게 원인을 알린다.
- 수정 범위는 최소로. 관련 없는 정리는 하지 않는다.

## 5. 회귀 시험과 확인
- 재현 명령이 이제 성공하는지 다시 실행하고, 버그를 잡는 시험을 하나 추가한다(tdd 스킬 참고).
- 전체 시험을 돌려 다른 곳이 깨지지 않았는지 확인한다.
